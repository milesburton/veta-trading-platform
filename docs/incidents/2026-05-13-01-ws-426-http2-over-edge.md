# Incident: Public WebSocket feed blocked by HTTP/2 at the OVH edge

- **Started**: not known precisely; first user report was on 2026-05-13 around midday UTC. Likely silently broken from the moment public TLS via OVH was wired up (PR #153, 2026-04-XX) but had been masked while traders used the LAN URL.
- **Resolved**: 2026-05-13 12:25 UTC
- **MTTR**: ~50 min from first verified reproduction
- **User-visible impact**: dashboard loaded but the Feed indicator stayed red ("disconnected"). Live prices, order updates and trade actions were paused for any user accessing `veta.mnetcs.com`. Direct LAN access via `http://192.168.1.245/` was unaffected.
- **Detection**: user-reported repeatedly throughout 2026-05-12 and 2026-05-13. The synthetic-monitoring Phase 4 from the operations strategy would have caught this in under 60s; that phase has not yet been implemented.
- **Severity**: SEV2

## What happened

Modern browsers prefer HTTP/2 when the server advertises `h2` via TLS ALPN. Traefik 3 advertises `h2` by default on any websecure entrypoint. The OVH edge therefore served `veta.mnetcs.com` over HTTP/2.

The application's `/ws/gateway` endpoint is a WebSocket. RFC 6455 WebSockets only run over HTTP/1.1; RFC 8441 ("Bootstrapping WebSockets with HTTP/2") is a separate spec that the homelab Traefik does not implement. So when a browser tried to upgrade a WebSocket connection over HTTP/2, the homelab Traefik returned `HTTP/2 426 Upgrade Required`, the OVH edge passed that through, and the frontend's WebSocket client gave up after retrying.

Three things contributed to this being missed for so long:
1. LAN access bypasses the OVH edge entirely, so any developer testing on the LAN saw a working feed.
2. Existing Playwright tests use mocked WebSockets, so the wired-up feed path was never exercised end-to-end against the real edge.
3. The deploy-gate added in #202 runs against a freshly composed stack in CI, not against the actual OVH-fronted production URL.

## Root cause

`edge/dynamic.yml` (the OVH Traefik dynamic config) didn't restrict TLS ALPN, so the edge advertised both `h2` and `http/1.1`. Browsers picked `h2`, and the WebSocket upgrade then failed at the application layer.

## Fix

`edge/dynamic.yml` sets `tls.options.default.alpnProtocols` to `[http/1.1, acme-tls/1]`. Removing `h2` forces every TLS connection to negotiate HTTP/1.1, which is the protocol the WebSocket upgrade path expects. Plain HTTP requests (GET /, /api/gateway/ready, etc) continue to work; only the wire protocol changes from HTTP/2 to HTTP/1.1. For a single-replica origin behind an SSH-tunnelled backend, HTTP/2 multiplexing wasn't buying us measurable performance anyway.

An earlier attempt to use `serversTransports.tunnel-http1.disableHTTP2: true` on the OVH→homelab leg was abandoned: it appears Traefik 3.3 silently ignores that field when set via dynamic config alongside an inline `servers` block. Restricting ALPN at the entrypoint is more reliable and covers the browser-to-OVH leg, which is where the protocol negotiation actually fails.

Reliability work uses a small set of overloaded acronyms. The terms come from Google's SRE practice and have been adopted by Netflix, Stripe, every major exchange, and most fintechs that handle real money. This page defines each one **as VETA uses it**, so any other doc can refer to "SLO" or "error budget" without re-explaining.

The vocabulary matters because it forces clarity. "The platform is unreliable" is a complaint. "We've burned 110% of our 30-day availability error budget and are entering reliability-only mode for the next two weeks" is a plan.

## The four-term core

### SLI: Service Level Indicator

**What you measure.** A single, well-defined metric about the user-facing behaviour of the system.

Good SLI:

> "Percentage of requests to `/api/gateway/api/oms/orders` that return HTTP 2xx within 500ms."

Bad SLI:

> "CPU usage on the homelab." This is an internal system metric, not user-facing.

An SLI is a number you can compute from telemetry, expressed as a ratio or percentage. VETA's SLIs come from Loki query results, gateway access logs, and the [synthetic probe](../../platform/operations-strategy/target-architecture/#synthetic-monitoring-shipped).

### SLO: Service Level Objective

**The target** for that indicator over a defined time window. The objective is a promise the platform team makes about user-visible behaviour.

> "99.9% of requests to `/api/gateway/api/oms/orders` will return 2xx within 500ms, measured over a rolling 30 days."

Two components: a number (99.9%) and a window (30 days). The window matters because it bounds the math. A 1-hour outage on an annual SLO is different from the same outage on a monthly SLO.

SLOs are **the right number, not the highest possible number**. 99.9% is a useful target; 100% is impossible (every system has dependencies that fail) and pursuing it makes the team afraid to ship. The SRE book's standard advice: pick the lowest reliability number that keeps users happy. For VETA's public-demo level we picked 99.9%, generous enough to absorb a few minutes of deploy turbulence per month and tight enough to mean something.

### SLA: Service Level Agreement

**The contract** with users if the SLO is missed. Usually involves money: refunds, service credits, contractual penalties.

> "If monthly availability drops below 99.0%, we credit 10% of monthly fees."

The SLA bound is **always looser than the SLO** so the team has a buffer between "we promised internally" and "we owe money externally."

VETA today has no paying users, so no SLA. The framing is still useful: when you imagine the SLA you'd offer, it forces you to make the SLO honest.

### Error budget

**The downtime you're allowed to spend** before missing the SLO.

Mechanically:

> `error_budget = (1 − SLO) × time_window`

So:

| SLO | Monthly budget | Yearly budget |
| --- | --- | --- |
| 99% | 7h 18m | ~3.65 days |
| 99.5% | 3h 39m | ~1.83 days |
| 99.9% | 43m 12s | ~8h 45m |
| 99.95% | 21m 36s | ~4h 22m |
| 99.99% | 4m 19s | ~52m 35s |
| 99.999% | 25.9s | ~5m 15s |

The error budget is the mechanism that **gives the engineering team permission to take risks**. If we have 30 minutes of budget left this month, we can ship a risky change. If we've already burned 60 minutes, we don't. This is the single most important consequence of SLOs: they make the **risk vs. velocity** trade-off explicit, instead of leaving it to a manager's gut.

<Aside type="note" title="Error budget policy">
An SLO without a budget policy is theatre. The policy says what happens when the budget is exhausted. Standard form:

- Budget healthy → ship features at normal cadence.
- Budget consumed > 75% → require additional review on risky changes.
- Budget exhausted → freeze feature work; reliability fixes only.
- Two consecutive budget-exhausted periods → executive review.

VETA's policy lives in the [operations strategy](../../platform/operations-strategy/).
</Aside>

## Recovery and detection metrics

### MTTR: Mean Time To Recovery

**How long an incident lasts.** From the moment a page-able alert fires (or the issue becomes user-visible) until the system is verifiably healthy again.

Industry distinction worth knowing:

- **MTTA** (Mean Time To Acknowledge): alert fires to human sees it. Bounded by on-call response, not engineering.
- **MTTD** (Mean Time To Detect): incident starts to alert fires. Bounded by monitoring quality. If you find out via a user report, your MTTD is hours; if you find out via a synthetic probe, it's a minute.
- **MTTR** (Mean Time To Recovery): alert fires to green again. Bounded by tooling: runbooks, automation, rollback speed.

A high MTTR with low MTTD says "we detect fast but recover slow"; the fix is rollback automation. A high MTTD says "we don't know we're broken"; the fix is synthetic monitoring.

VETA's target is **MTTR < 30 minutes** on SEV1, **MTTD < 5 minutes** once synthetic probes are live.

### MTBF: Mean Time Between Failures

How often incidents happen. Less useful than the other M-metrics because:

- It rewards hiding problems (never declare an incident, so MTBF goes up).
- It punishes good detection (better monitoring leads to more "incidents", so MTBF goes down even though reliability improves).

Tracked but not targeted. The team metric is "did we hit our SLO?", not "did we have few incidents?"

## Recovery scope: RPO and RTO

These come up in disaster recovery, less so in routine operations.

### RPO: Recovery Point Objective

**The maximum data loss tolerated** measured in time. If your RPO is 5 minutes, you must be able to restore the system to a state no more than 5 minutes before the disaster.

Determines backup cadence:

- RPO 24h: daily backup is enough.
- RPO 1h: hourly backup, or continuous WAL shipping.
- RPO 5m: streaming replication with synchronous or near-synchronous commits.
- RPO 0: multi-region synchronous writes, very expensive.

VETA's target is **RPO < 5 minutes**, achieved by Postgres streaming replication once Phase 6 of the operations strategy lands.

### RTO: Recovery Time Objective

**The maximum time to recover** from disaster. If your RTO is 30 minutes, the system must be back online within 30 minutes of total loss.

Determines runbook quality and automation:

- RTO 24h: manual restore from cold backup is OK.
- RTO 1h: tested runbooks, manual failover.
- RTO 30m: mostly-automated failover, on-call must be alerted.
- RTO 5m: fully automated failover with no human in the loop.

VETA's target is **RTO < 30 minutes**, achieved by pg-auto-failover (or Patroni) plus the documented disaster runbook.

## DORA metrics

[DORA](https://dora.dev/) (DevOps Research and Assessment) published research correlating four metrics with software-team performance. The four together describe **velocity** (deploy frequency, lead time) and **stability** (change failure rate, MTTR). Real platforms track all four.

| Metric | Definition | Elite | High | Medium | Low |
| --- | --- | --- | --- | --- | --- |
| **Deployment frequency** | How often code reaches prod | Multiple per day | Daily-weekly | Weekly-monthly | Monthly+ |
| **Lead time for changes** | Commit to prod | < 1 hour | 1 day to 1 week | 1 week to 1 month | > 1 month |
| **Change failure rate** | % of deploys causing incidents | 0-15% | 16-30% | 16-30% | 16-30% |
| **Failed deployment recovery time** | Time to recover from a failed deploy | < 1 hour | < 1 day | 1 day to 1 week | > 1 week |

(Bands as published in the 2024 DORA report.)

The point of DORA is that **velocity and stability move together**. Fast teams are not less safe; they are more practised. The thing that makes them fast (small, frequent changes) is the same thing that makes them safe (small blast radius, quick rollback).

VETA today is **Elite** on velocity (multiple PRs per day, < 1h lead time) and **Low** on stability (change failure rate around 40%, MTTR sometimes hours). The operations strategy closes the stability gap without sacrificing velocity.

## Severity levels

How urgently we treat an incident. Used to decide alerting cadence, on-call wake-up rules, and postmortem requirements.

| Level | Definition | Example | Response |
| --- | --- | --- | --- |
| **SEV1** | Full outage. Users cannot do core work. | Site returns 404, can't sign in, can't submit orders. | Immediate page; root-cause postmortem mandatory. |
| **SEV2** | Major degradation. Core work possible but degraded. | Live feed stuck on a stale value; order ack p99 > 5s. | Same-day investigation; postmortem if user-visible > 5 min. |
| **SEV3** | Minor degradation or contained bug. | Single panel rendering issue; non-critical service slow. | Tracked but no page; fix on next regular cycle. |
| **SEV4** | Cosmetic / informational. | Slow icon load; typo in error message. | Backlog. |

Severity is **about user impact**, not internal complexity. A 1-line bug that breaks sign-in is SEV1. A 1000-line refactor that nobody notices is not even an incident.

## Other terms you'll see in the strategy doc

| Term | Meaning |
| --- | --- |
| **Blast radius** | How much is affected by a single failure. Smaller = safer. Rolling deploys have smaller blast radius than batch deploys. |
| **Blue-green deploy** | Run two complete environments in parallel; switch traffic atomically. Old environment stays warm for fast rollback. |
| **Canary** | Roll a change out to 1% of traffic first; observe; expand if healthy. Smaller blast radius than blue-green for some classes of bug. |
| **Chaos engineering** | Deliberately injecting failures (kill a container, drop a network link) to verify the system recovers. Netflix's Chaos Monkey is the famous example. |
| **Circuit breaker** | A pattern where a failing dependency is detected and calls to it are short-circuited rather than queued, so failure doesn't cascade. VETA has these in the [risk architecture](../../platform/risk-architecture). |
| **Drain** | Stop sending new work to a node so it can be safely shut down. Swarm and Kubernetes both do this for rolling deploys. |
| **On-call / pager** | A named human responsible for responding to alerts during a shift. Modern teams rotate weekly. Today VETA's pager is `veta@mnetcs.com`. |
| **Postmortem** | Written record of what happened, why, and what changes prevent recurrence. Blameless: people are not named except as note-takers. |
| **Rollback** | Returning a system to a known-good state, fast. Distinct from "fix forward" (deploy a patch). Rollback should always be the first option. |
| **Runbook** | A documented procedure for handling a known operational event. Good runbooks make MTTR predictable. |
| **Toil** | Manual repetitive work that scales linearly with system size. SRE practice aims to keep toil < 50% of an engineer's time; the rest goes to automation. |

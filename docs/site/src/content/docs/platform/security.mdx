This page describes the container-level defences applied to the trading
stack, the residual risks we have not addressed, and the
operational steps required when rolling out hardening changes to the
server.

## Threat model

The primary attacker we defend against is a remote actor with network
access to the trading network (a LAN attacker on the server, or someone
who has compromised a public-facing service reachable through the edge server
at the deployment URL). The exploit chain
of greatest concern:

1. Find a remote-code-execution bug in any internet-reachable service
   (gateway, frontend, public-facing health endpoints).
2. Get shell as that service's UID inside its container.
3. From there, attempt to read data the service shouldn't access,
   move laterally to other containers, or escape to the host.

The defences below are arranged so that each step in the chain has a
hurdle, and the hurdles tighten as you move closer to host compromise.

## Defences in place

### Capability dropping

Every container drops all Linux capabilities (`cap_drop: [ALL]`) and
selectively re-adds only what the workload genuinely requires:

| Service | Capabilities added back | Why |
| --- | --- | --- |
| `traefik` | `NET_BIND_SERVICE` | bind 80/443 as non-root |
| `postgres` | `CHOWN`, `DAC_OVERRIDE`, `FOWNER`, `SETGID`, `SETUID` | initdb permission setup |
| All others | none | Deno runtimes, kafkajs clients, ollama, kafka-relay |

Without capabilities, an in-container attacker cannot raw-socket scan,
modify network namespaces, or override file permissions outside their
own UID's reach.

### `no-new-privileges`

Every container is started with `security_opt: ["no-new-privileges:true"]`.
This blocks setuid escalation: even if an attacker finds a setuid binary
inside the container, the kernel refuses to honour the bit. The class of
"defeat the non-root constraint" exploits is closed off.

### Non-root execution (Deno services)

The shared base Dockerfile (`docker/base/Dockerfile`) ends with
`USER deno:deno`, mapping all Deno-based trading services to UID 1993
inside their containers. An attacker who lands RCE has the privileges
of UID 1993, not 0. Combined with capability drop, the post-exploit
position is meaningfully constrained.

The infrastructure containers (`postgres`, `redpanda`, `traefik`,
`ollama`) run as their official-image user models. Those upstream
images already enforce non-root execution internally.

### Read-only-by-default disk-monitor

The disk-monitor container previously had access to the Docker socket
(read-write) and mounted the entire host filesystem. That made it the
single highest-blast-radius container in the stack: an RCE there would
yield full host control via the Docker API. The container is now:

- `read_only: true` filesystem
- `cap_drop: [ALL]`, `no-new-privileges`
- `user: 65534:65534` (nobody)
- No Docker socket mount
- Host filesystem mounted **read-only** at `/host`

The container can report disk usage; it cannot prune images, start
containers, or write anywhere. Image pruning is now an out-of-band cron
on the host (see `scripts/host-prune.sh`).

### `tmpfs:/tmp`

Each Deno service gets `/tmp` as a tmpfs mount. Anything that does land
in `/tmp` exists only in RAM and dies with the container. Nothing
persists, and no on-disk artefacts survive a restart.

### WebSocket abuse tracking

<Source path="backend/src/gateway/abuse-tracker.ts" label="AbuseTracker" />

The gateway's `AbuseTracker` produces escalating decisions against a WebSocket connection and the user behind it:

- **Level 1** (handled by the per-socket frame rate limiter, not `AbuseTracker`): reject a single over-rate frame and send `rateLimited` back to the client. Soft, no state kept.
- **Level 2** (`AbuseTracker.recordRateLimited`): a single socket hits the per-socket frame limit `ABUSE_PER_SOCKET_THRESHOLD` times within `ABUSE_PER_SOCKET_WINDOW_MS`. Decision: `forceClose`. The socket is closed and a `ws_disconnected_abuse` access event is published.
- **Level 3** (`AbuseTracker.recordRateLimited` escalating further): a single userId accumulates `ABUSE_USER_FORCE_CLOSE_THRESHOLD` force-closes within `ABUSE_USER_WINDOW_MS`. Decision: `blockUser`. New WebSocket upgrade attempts for that userId are refused for `ABUSE_USER_BACKOFF_MS`, checked by `AbuseTracker.upgradeDecision` before `Deno.upgradeWebSocket` runs.

There is no IP-banning. UserIds are the control surface: unauthenticated sockets share a single anonymous key, so level-3 effects on anonymous traffic apply globally. That matches the threat model above: a real attacker authenticating anonymously is just one of many anonymous callers, so anonymous traffic as a whole is the unit of defence.

All state is in-memory and resets on a gateway restart. That is an accepted trade-off: the structural protection (level 2's force-close ending a chatty client's connection) re-establishes naturally on the client's next request, so a restart does not reopen a window for sustained abuse.

<Source path="backend/src/gateway/routes/websocket.ts" region="docs:ws-upgrade-auth-order" />

Authentication happens before the WebSocket upgrade completes, not after: once a connection is upgraded, there is no way to send an HTTP 401 back to the client, only WebSocket frames. Anonymous connections are still allowed to complete the upgrade, since read-only market data does not require a session. The client IP and User-Agent are also captured once at upgrade time, since `req.headers` is unavailable after the upgrade but both are needed later for the per-IP guest order-submit rate limit and access-event tagging. Auth is resolved eagerly (awaited) before the abuse check runs, so `upgradeDecision` knows which user it is deciding for; if the upgrade is allowed, the same resolved `pendingAuth` is reused for the socket instead of re-validating the token a second time.

## Frontend input hardening

<Source path="frontend/src/store/safeKey.ts" label="isSafeKey" />

`isSafeKey` guards against prototype-pollution and remote-property-injection when a `Record<string, T>` is indexed by a key that originated from external input (a Kafka payload relayed to the browser, a gateway message, or a `?query=` parameter). It rejects `"__proto__"`, `"constructor"`, `"prototype"`, any key containing non-printable characters, and any value too long to plausibly be a legitimate id, before that key is ever used to index a plain object.

<Source path="frontend/src/hooks/useWorkspaceSync.ts" label="SHARED_WORKSPACE_ID_RE" />

Shared workspace IDs are always created server-side as alphanumeric tokens. `useWorkspaceSync` validates an incoming `?shared=` URL parameter against that same shape before issuing a fetch for it: anything containing slashes, dots, or query characters cannot be a real workspace id, so the request is rejected client-side rather than letting a hostile `?shared=` URL get forwarded as part of a request path to a different endpoint.

## Residual risks (not yet mitigated)

### `read_only: true` not yet applied to Deno services

The Deno-based trading services are *not* yet read-only. They could be:
they don't write to local disk at runtime (logs go to stdout, state goes
to Postgres or Kafka). The reason it isn't done in this pass is that
the failure mode of getting it wrong on a live server (one service
crashes in a restart loop on next deploy) outweighs the marginal defence:
the trading containers are stateless and an RCE attacker only owns them
for the lifetime of that container instance.

This is on the queue for a future pass once each service has been
individually verified as filesystem-clean.

### User-namespace remapping

Docker can be configured to remap container UIDs to a high host UID
range (`userns-remap`), so even "root in container" is a low-privileged
host user. This would substantially harden the residual privileged
containers (Postgres, Traefik with its docker-socket mount). It is invasive
(every existing volume needs UID migration) and is queued as its own
session.

## Disk-prune cron

To schedule a weekly host-level docker prune:

```bash
sudo crontab -e
# Add:
0 4 * * 0 /opt/stacks/veta/scripts/host-prune.sh >> /var/log/veta-prune.log 2>&1
```

## Verification

After the hardened stack is deployed, confirm capabilities are dropped:

```bash
docker inspect veta-gateway-1 --format '{{ .HostConfig.CapDrop }}'
# Expect: [ALL]
docker inspect veta-gateway-1 --format '{{ .HostConfig.SecurityOpt }}'
# Expect to include: no-new-privileges:true
docker exec veta-gateway-1 id -u
# Expect: 1000 (deno)
```

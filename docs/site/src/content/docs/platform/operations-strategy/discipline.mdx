## Every change reaches production through CI, full stop

No exceptions for outages. No direct edits to the running production configuration or code, ever — not a config tweak, not a "just this once" restart with a patched file copied in, not with explicit sign-off from anyone, including the platform owner, given in the moment. The only path from a change to production is: branch, fix, open a PR, wait for every required check to genuinely pass, merge, then the normal deploy pipeline.

This also means merges never bypass required status checks. A merge command that skips branch protection (an admin override, or equivalent) is not available as a tool for getting an urgent fix out faster — if checks are slow or flaky, the fix is to make CI faster or fix the flake, not to go around it.

**Why this is absolute rather than a guideline:** this platform models real trading discipline. An untested or unreviewed change reaching a live trading system during a trading day is not a process shortcut with an acceptable trade-off against faster recovery — it is the specific failure mode that pre-trade checks, staged rollouts, and required review exist to prevent. Speed during an incident comes from a fast pipeline, not a skipped one. See the [2026-08-23 market-sim incident](https://github.com/milesburton/veta-trading-platform/blob/main/docs/incidents/2026-08-23-01-market-sim-oom-loop.md) for what this looks like when it goes wrong.

## Rollback plans in every PR

Every PR description must answer: "How do we roll this back if it breaks prod?" Three classes:

- **Pure code change**: revert the commit, redeploy. Default; needs no special handling.
- **Schema migration**: must include a working `down` migration AND be deployed in two phases: expand (schema accepts old + new code), then contract (after rollout settles), then drop (after a soak). Single-phase migrations are forbidden.
- **Config / env change**: captured in version control; rollback is reverting the config commit, never editing on the box.

The PR template enforces this with a required `## Rollback plan` section.

## Incident log

A `docs/incidents/` directory. Every incident gets a timestamped file with:

- When (UTC start, UTC end)
- What (user-facing symptom)
- Root cause
- <Term name="mttr" /> (Mean Time To Recovery)
- Detection (synthetic / user-reported / log alert)
- Action item with owner + deadline (e.g. "add test that catches this class. Owner: M, by: 2026-05-19")

Backfilled with 2026-05-12 incidents as the first entries. Patterns become visible after ~10 entries.

## Postmortems

Blameless template, lives in the same directory. Required for any incident with <Term name="mttr" /> > 30 min OR user-visible impact > 5 min. Three sections only: **What happened (timeline)**, **What went well**, **What we'll change**. No long apologies; no individuals named except as note-takers.

## Change-freeze windows

`scripts/deploy.sh` checks for an active freeze window (file or env var) and refuses to deploy without an explicit `--hotfix` flag, which is logged. Typical freezes:

- Demo windows (announced in advance)
- The first 30 min after another deploy (let the platform settle)
- Weekends outside hotfixes

Cheap to implement, prevents the "user is watching the dashboard while the deploy trashes it" scenario from 2026-05-12.

## On-call rotation (future)

Solo project today, but worth defining the shape. When a second person joins, on-call becomes a named role with a known pager (email / Discord / SMS). Until then, the synthetic probe still emails `the ops email` and we treat it as the pager.

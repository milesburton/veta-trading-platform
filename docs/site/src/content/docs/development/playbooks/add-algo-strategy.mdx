## When to use

You are adding a new execution algorithm (e.g., `OPPORTUNISTIC`, `LIQUIDITY-SEEKING`) that consumes the parent-order stream and emits child orders.

## Inputs needed

- A docker-compose stack running locally so the bus exists (`docker compose up -d redpanda`)
- Familiarity with the [Algo strategies](/veta-trading-platform/platform/algos/) page

## Steps

1. **Create the strategy file** at `backend/src/algo/<lowercase-name>-strategy.ts`. Pattern to follow: [`backend/src/algo/twap-strategy.ts`](https://github.com/milesburton/veta-trading-platform/blob/main/backend/src/algo/twap-strategy.ts) is the most digestible reference. Required behaviour:
   - Subscribe to `orders.routed` for parents that name your strategy
   - Read fill progress from the journal with `readSliceBudget()` from `fill-progress.ts`, not from local counters (see [Fill progress from the journal](#fill-progress-from-the-journal))
   - Publish to `orders.child` for each child slice you generate
   - Emit `algo.heartbeat` when an order starts, slices and completes. These are order-lifecycle events, not a periodic keepalive (see [Algo heartbeats are not a liveness signal](/veta-trading-platform/platform/observability/alerts/#algo-heartbeats-are-not-a-liveness-signal))
   - Cap each child with the shared depth cap in `depth-cap.ts` unless the algo sizes children from tick volume or available quantity (see [Child order sizing](/veta-trading-platform/user-guide/algo-trading/#child-order-sizing))
2. **Register the service.** Use the next free port in the 5000-range and add the service to each place that lists services:
   - `compose.yml` and `compose.prod.yml`, with an `image:` override in the latter
   - `supervisord.conf`, `shared/serviceRegistry.ts` and the `docker/<name>/Dockerfile`
   - the `docker-services` matrix in `.github/workflows/ci.yml` (see [CI/CD](/veta-trading-platform/development/ci-cd/#docker-services-3-to-5-minutes-per-image-parallel))
   - `compose.observability.yml`, for its `OTEL_SERVICE_NAME`
   - `<UPPER>_ALGO_PORT` and `<UPPER>_ALGO_HOST` in the `gateway` service env block so `SVC_PROXY` can route to it
   - the service descriptions in `docs/site/scripts/generate-service-map.mjs`
3. **Update the params type** in `frontend/src/types.ts`. Add a `<Name>Params` interface and union member in `AlgoParams`.
4. **Add the strategy name** to the shared strategy list in `shared/primitives.ts` and to the frontend lists in `domain/market/venueCapabilities.ts`, `domain/market/marketSession.ts` and `domain/ticket/fieldDefinitions.ts`. Add a colour for it in `frontend/src/tokens.ts` (see the [style guide](/veta-trading-platform/development/style-guide/)), an entry in `StartupOverlay/serviceCatalog.ts`, and a `/api/<name>` proxy rewrite in `frontend/vite.config.ts`.
5. **Wire the order-ticket UI** by adding a strategy option in [`StrategyParams.tsx`](https://github.com/milesburton/veta-trading-platform/blob/main/frontend/src/components/StrategyParams.tsx). Add a builder branch in [`OrderTicket/buildAlgoParams.ts`](https://github.com/milesburton/veta-trading-platform/blob/main/frontend/src/components/OrderTicket/buildAlgoParams.ts).
6. **Document** in the strategy file's leading JSDoc. The first line becomes the title and the body becomes the description on [Algo strategies](/veta-trading-platform/platform/algos/) — picked up automatically by `docs/site/scripts/generate-algos.mjs` on the next docs build.

## Verification

```bash
# Unit tests for the new strategy
npx vp test run backend/src/tests/algo.unit.test.ts

# Testcontainers integration (starts the algo and submits a parent order)
npm run test:testcontainers

# Frontend tests covering the new strategy in OrderTicket
cd frontend && ./node_modules/.bin/vitest run src/components/OrderTicket/

# Docs site rebuild picks up the new algo
cd docs/site && npm run generate
```

## Common pitfalls

- **Forgetting the heartbeat**: the algo feed indicator in the status bar only turns live when `algo.heartbeat` events arrive. The helpers in `common-http.ts` and `fill-progress.ts` build the heartbeat payloads; use them.
- **Hardcoding venue selection** — child orders should let the EMS choose the venue (see [Smart Order Router](/veta-trading-platform/platform/smart-order-router/)). Only set `venue` explicitly if your algo is doing best-price routing like SNIPER.
- **Registration**: `npm run check` type-checks the whole `backend/` tree and the unit tests are discovered by glob, so a new strategy file and its tests need no registration.
- **Docs auto-gen swallows your description** — the algo generator reads the first sentence (split on `. <Capital>`). Keep the first sentence punchy.

## Execution mechanics reference

The existing drift-sensitive algos share two patterns worth reusing rather than reinventing.

### Adverse-drift sign convention

<Source path="backend/src/algo/is-strategy.ts" region="docs:is-adverse-drift" />

Raw drift (`(marketPrice - arrivalPrice) / arrivalPrice`) is signed relative to price direction, not relative to the order. Whether a given drift is adverse depends on the order's side: for a BUY, a price rise is adverse (the fill costs more than the arrival price); for a SELL, a price fall is adverse (the fill returns less). `adverseDriftBps` flips the sign for SELL orders so that "positive adverse drift" always means "the market moved against this order," letting the rest of the algo (pause/resume, acceleration) reason about a single sign convention regardless of side.

### Accelerating on favourable drift

<CodeBlock
  path="backend/src/algo/is-strategy.ts"
  region="docs:is-acceleration-and-tolerance"
  title="IS: acceleration and aggression tolerance"
/>

When adverse drift is negative (the market is moving in the order's favour), the next-slice interval is cut by 20% to capture more of the favourable move before it reverses. The child limit price also carries a small aggression tolerance (0.5 bps of market price) on the far side of the market (above for BUY, below for SELL), which produces passive-ish limit orders that still have a high probability of filling against normal market movement, rather than resting exactly at the current price and potentially missing fills entirely.

<Source path="backend/src/algo/arrival-price-strategy.ts" region="docs:arrival-price-urgency-scaling" />

ARRIVAL_PRICE uses a similar 20%-acceleration-on-favourable-drift rule, but scales its base slice interval by `urgency / 50` first: `urgency=50` is the neutral point (1x pace), `urgency=100` doubles the pace, and `urgency=25` halves it. Keep this convention (50 as the neutral midpoint of a 0-100 urgency parameter) if a new algo exposes a similar urgency knob, so the parameter behaves consistently across algos from a trader's perspective.

### Fill progress from the journal

<Source path="backend/src/algo/fill-progress.ts" label="Journal-backed fill progress" />

TWAP, VWAP, POV and LIMIT do not count their own fills. Sending a child order is not the same as filling it: the matching engine can partially fill a child or fill none of it, and EMS children are IOC, so a zero fill produces no event. Before each slice the algo calls `readSliceBudget()`, which reads `GET /journal/order/:id/progress` (filled quantity, average price and filled child IDs, summed from `orders.filled` rows) and returns the quantity still to send.

At most one child is in flight per parent order. A child counts against the remaining quantity until its ID appears in `filledChildIds` or `ALGO_CHILD_SETTLE_MS` (default 3000) elapses, after which it is treated as unfilled and the quantity becomes available again. If the journal is unreachable the slice is skipped rather than sent blind.

`startJournalProgressSweep()` in `common-http.ts` polls the same endpoint every 5s and removes each order once it is complete (publishing a `complete` heartbeat) or expired (publishing `orders.expired` with the journal's filled quantity).

### Claim before await

Tick handlers run on a single-threaded event loop, but each `await` yields, so a second tick can re-evaluate an order while a journal read or `producer.send()` is in progress. VWAP, POV and LIMIT add the order to an `evaluating` set before their first `await` and skip any order already in it. Order state is replaced through `setInFlight()`, which only updates an entry still present in the map, so a sweep that removes an order mid-evaluation is not undone. A new algo with the same shape should follow both rules.

### Front-loaded slice schedules

<CodeBlock
  path="backend/src/algo/is-strategy.ts"
  region="docs:is-slice-schedule"
  title="IS: geometric slice schedule"
/>

IS front-loads its child order sizes using geometric decay: `rawWeight[i] = urgency * (1 - urgency)^i`, normalised to sum to the total quantity. The number of slices scales from `minSlices` (low urgency) to `maxSlices` (high urgency), which is the opposite of what the geometric decay alone would suggest. Higher urgency concentrates more of the *quantity* into the earliest slices (the decay is steeper), but the schedule still allocates the full `maxSlices` range so there is enough resolution in the tail; it is the slice quantities, not the slice count, that do the front-loading work.
